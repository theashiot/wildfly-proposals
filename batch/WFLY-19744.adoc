= Provide a way to detect abnormal job executions after a server crash and give users a way to deal with these executions in bulk/automatic ways

:author:            Ashwin Mehendale
:email:             amehenda@redhat.com
:toc:               left
:icons:             font
:idprefix:
:idseparator:       -

== Overview

A batch job execution that stops making progress has no supported way back to a usable state. A batch job can stop making progress in the following cases (not-exhastive):

* Server crash.
* Server shutdown without specifying a timeout.
* Server reload.
* A step block indefinitely on a remote call.

This document propose the following runtime-only management operations to the `batch-jberet` subsystem's deployment-scoped job resource backed by two new methods on the JBeret job operator:

[source,terminal,options="nowrap"]
----
/deployment=batch-app.war/subsystem=batch-jberet/job=importOrders:list-executions-not-updated-in-minutes(minutes=30, start=0, count=3)
----

[source,terminal,options="nowrap"]
----
/deployment=batch-app.war/subsystem=batch-jberet/job=importOrders:fail-job-execution(execution-ids=[123, 456, 789])
----

=== User Stories

* As a system administrator, I want to find potentially unresponsive job executions, so that I can move them to the FAILED status.
* As a system administrator, I want to transition potentially unresponsive job executions to the FAILED status, so that I can restart them.
* As a developer, I want to create batchlet that can transition the jobs suspected to have crashed (based on configurable value of time elapsed since the last checkpoint) to the FAILED status, so that I can restart them.

== Requirements

Two runtime-only operations are registered on the deployment-scoped `job` resource:

* The `list-executions-not-updated-in-minutes` operation takes a required `minutes` parameter and optional `start` and `count` parameters defaulting to `0` and `100` and returns the execution-ids of executions that are in the `STARTED` or `STOPPING` state and have not updated their `lastupdatetime` for the past `minutes` duration.
+
The cut-off must be computed from the calling JVM's clock, since
that is the clock  with which JBeret writes the column.

* The `fail-job-execution` operation takes a required
`execution-ids` list of one to 1,000 values and returns `failed-count`, `failed-execution-ids`,
`skipped-count` and `skipped-executions`, each skip paired with a reason.
It transitions
partition executions, then step executions, then the job execution to `FAILED` with an exit status of `FAILED_BY_ADMIN` by default, leaving anything already in `COMPLETED`, `FAILED`, `STOPPED` or
`ABANDONED` untouched. Additionally:

** All job accepted executions must be failed in one transaction, driven from the JDBC layer on a single connection.

** Job executions that are absent, out of scope, in the wrong state, or detectably running in the local JVM are skipped without aborting the operation

=== Non-Requirements

This enhancement is not about making conclusive determination about whether job executions have crashed. Rather, this enhancement provides users a way to make their own determination based on the time elapsed since the last database update made by a job execution.

=== Future Work

A futher enhancement that should be considered in the future is to automatically determine whether a job has crashed.

== Backwards Compatibility

Both proposed operations are runtime-only operations on existing deployment resources,
and the JBeret-side additions are new interfaces, new value types and `default` interface methods.
Therefore, not backwards compatibility concerns apart from the one mentioned under "Deplyments".

=== Default Configuration

No current configuration attribute changes its default value, and no Galleon layer produces different configuration.

=== Importing Existing Configuration

An existing configuration runs unchanged, and no change to the WildFly server migration tool is needed.

=== Deployments

A deployment whose `permissions.xml` grants
the five existing permission names (`start`, `stop`, `restart`, `abandon`, `read`) explicitly, rather than granting `pass:[*]`, will see `JobSecurityException` when it
or a management client attempts `fail-job-execution` against it.
Adding `fail` to the grant resolves it.
Deployments granting `pass:[*]`, and deployments that do not configure `BatchPermission` at all, are
unaffected.

== Community Documentation

A new section in the batch subsystem admin guide documents the stale-execution workflow end to end: 

* How to identify potentially stuck executions with `list-executions-not-updated-in-minutes`. 
* how to choose a `minutes` value relative to the job's checkpoint interval.
* How to fail and then restart job executions.

Caveat about job execution potentially being alive on another nod will be added.

== Release Note Content

As an administrator, you can now list the jobs that are in the `STARTED` or the `STOPPING` state but whose last-updated time has not moved within a given window indicating that they might be stuck. You can then transition the job executions that you determine are stuck to the `FAILED` state. Transitioning job executions to the `FAILED` state provides you with the opportunity to restart the jobs.
